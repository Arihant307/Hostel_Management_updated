# Hostel Management System

A full-stack hostel management web application. It has a **Flask** REST API with **SQLAlchemy** and **SQLite**, and a **React (Vite) + Tailwind CSS** frontend. There are four roles: **admin**, **warden**, **staff** and **student**.

People can create their own accounts:
- **Students** sign up, verify their email, and are approved by the hostel office.
- **Staff** need either an invitation from an administrator or an administrator's approval.
- **Everyone** can recover a forgotten password by email.

> **Status: complete.** 230 automated backend tests pass (on SQLite and PostgreSQL). The signup, verification, approval, login, password reset and logout flows were checked in a browser against the real API and database. [Known limitations](#known-limitations) lists what is deliberately not included.

## Deploying to Render (free)

Everything below uses free plans and needs no credit card.

| Part | Where | Free plan notes |
|------|-------|-----------------|
| React frontend | Render **Static Site** | Always on, served from a CDN |
| Flask API | Render **Web Service** (free) | Sleeps after 15 idle minutes; the first request then takes about a minute |
| Database | **Neon** PostgreSQL | 1 GB per project; no 30-day expiry like Render's free Postgres |
| Email | **Brevo** HTTPS API | 300 emails/day. Render's free web services **block SMTP ports**, so Gmail SMTP does not work there |

The API reads everything from environment variables. Your local `backend/.env` and
`frontend/.env` are **never** uploaded (`.gitignore` excludes them).

### Step 1: Create the Neon database
1. Sign up at <https://neon.com> (you can use GitHub to sign in).
2. **Create project**: name `hostel`, region **AWS Asia Pacific (Singapore)** (closest to India).
3. Click **Connect** and copy the connection string. It looks like
   `postgresql://neondb_owner:...@ep-xxxx.ap-southeast-1.aws.neon.tech/neondb?sslmode=require`.
   Keep it secret.

The tables are created automatically on the first deploy (`flask db upgrade` runs at every start).

### Step 2: Set up Brevo for email
1. Sign up at <https://www.brevo.com> (Free plan).
2. **Add a sender:** open the account menu, then **Senders, Domains & Dedicated IPs → Senders → Add a sender**.
   Enter your name and the Gmail address the emails should come from, then confirm the code Brevo emails you.
3. **Create an API key:** **SMTP & API → API Keys → Generate a new API key**. Copy it (it starts with `xkeysib-`).
   It is shown only once.

Brevo adds a small "Sent with Brevo" footer on the free plan. Emails sent from a
`@gmail.com` address through another service can land in **Spam**; tell users to check it.

### Step 3: Push the code to GitHub
See [Upload to GitHub](#upload-to-github) below.

### Step 4: Create the Blueprint on Render
1. <https://render.com> → **Sign up with GitHub**.
2. **New + → Blueprint** → choose your repository. Render reads `render.yaml` and shows two services:
   `arihant-hostel-api` (web service, Free) and `arihant-hostel-app` (static site).
3. Fill in the values Render asks for:

   | Variable | Service | Value |
   |----------|---------|-------|
   | `DATABASE_URL` | api | Neon connection string from Step 1 |
   | `FRONTEND_URL` | api | `https://arihant-hostel-app.onrender.com` |
   | `BREVO_API_KEY` | api | Brevo API key from Step 2 |
   | `MAIL_DEFAULT_SENDER` | api | `HostelHub <your-verified-sender@gmail.com>` (the sender verified in Brevo) |
   | `ADMIN_EMAIL` | api | Email you will use to sign in as admin |
   | `ADMIN_PASSWORD` | api | 10+ characters with an uppercase letter, a lowercase letter and a digit |
   | `VITE_API_BASE_URL` | app | `https://arihant-hostel-api.onrender.com/api` |

   `SECRET_KEY` and `JWT_SECRET_KEY` are generated by Render automatically.
4. Click **Apply** and wait about 5 minutes for both services to deploy.

### Step 5: Check the real URLs (important)
If a service name is already taken on Render, Render adds a random suffix, e.g.
`arihant-hostel-api-x7k2.onrender.com`. Open each service in the dashboard and look at the URL at the top.

- If the **API** URL differs: static site → **Environment** → fix `VITE_API_BASE_URL`, then
  **Manual Deploy → Clear build cache & deploy**. The address is built into the JavaScript, so a rebuild is required.
- If the **frontend** URL differs: API service → **Environment** → fix `FRONTEND_URL` → **Save, rebuild and deploy**.

### Step 6: Test it
1. `https://<api-url>/api/health` shows `"database": "ok"`.
2. Open the frontend URL and sign in with `ADMIN_EMAIL` / `ADMIN_PASSWORD`.
3. Create a student account. The verification email arrives (check Spam), the link opens the site,
   then approve the student under **Students** and sign in as that student.

If the API fails to start, its **Logs** tab names the missing or wrong setting, for example
`Production configuration is incomplete: FRONTEND_URL must be ...`.

## Features

**Authentication and accounts**
- **Sign up:** a page that asks for the account type (Student or Staff) and shows the matching form.
- **Email verification:** a single-use link that expires, with a resend option.
- **Approvals:** students are approved by wardens and admins. Staff applications are approved or rejected by admins, who choose the role at approval.
- **Staff invitations:** single-use, tied to one email address, with an expiry. Admins can list and revoke them.
- **Password recovery:** forgot-password and reset-password pages.
- **Sign-in protections:** the same error whether an email is unknown or the password is wrong, and throttling after repeated failures.
- **Your account:** an Account page for editing your own profile, changing your password, and signing out here or on every device.
- **Admin tools:** account history (audit trail) for every user, a role-change dialog, and a button that emails a user a password-reset link.

**Admin dashboard.** Every figure is calculated from live database rows on each request:
- registered students, rooms, beds, occupancy %, pending fees, payments and active complaints
- recent registrations and allocations
- charts of monthly payments, occupancy by block, and complaints by category

**Other modules**
- **Students:** create, view, edit and deactivate. Filter by approval status, email verification, department, year and room. Deleting is allowed only for records with no history.
- **Rooms:** create, edit, deactivate, filter by availability, and see occupancy.
- **Room allocation:** allocate, transfer and check out. Capacity is enforced inside a transaction, and this was tested with simultaneous requests.
- **Fees and payments:** assign fees, generate monthly rent, record and reverse payments, print receipts, export CSV. Manually recorded payments are clearly labelled and are never treated as verified online payments.
- **Complaints:** students file them; staff assign, resolve, reply, and add notes only staff can see.
- **Notices:** pinned, scheduled, expiring, and targeted at an audience.
- **Reports (admin):** revenue, outstanding balances, occupancy and complaint figures, CSV exports and the audit log.

**User experience**
- A responsive navy design that fits a 375px phone screen without horizontal scrolling.
- Toast notifications, confirmation dialogs, loading skeletons, empty states and error messages on the field they relate to.

## Setup on Windows

Use **two terminals**: one for the backend and one for the frontend. These steps use **Anaconda Prompt** (cmd). PowerShell differences are noted.

### 1. Create a Conda environment for this project

```bat
conda create -n hms_env python=3.10 -y
conda activate hms_env
```

> Use a **separate** environment such as `hms_env`. If you already have an older `hostel_env` used by another project, leave it alone. This project needs newer Flask packages.

### 2. Install backend dependencies

```bat
cd hostel-management-system\backend
pip install -r requirements.txt
```

### 3. Configure the backend

```bat
copy ..\.env.example .env
notepad .env
```

- Replace the two `replace-with-…` values with two **different** random strings. Generate each with:
  ```bat
  python -c "import secrets; print(secrets.token_urlsafe(64))"
  ```
- Keep `MAIL_BACKEND=file` for local development. See [Email setup](#email-setup).
- Set `FRONTEND_URL` and `CORS_ORIGINS` to the address your frontend runs on (default `http://localhost:5173`).

### 4. Create or upgrade the database

```bat
flask db upgrade
```

### 5. Create the first administrator

```bat
flask create-admin
```

You'll be asked for an email, a name and a password. The password is typed hidden and entered twice. It needs at least 10 characters with uppercase, lowercase and a digit. No default admin or password exists anywhere in the code, and **admins can never be created through public signup**.

### 6. Start the backend (terminal 1)

```bat
flask run
```

Check it at `http://127.0.0.1:5000/api/health`. If port 5000 is busy, use `flask run --port 5001` and change the URL in step 8.

### 7. Install frontend dependencies (terminal 2)

```bat
cd hostel-management-system\frontend
npm install
```

### 8. Point the frontend at the API

Command Prompt:
```bat
echo VITE_API_BASE_URL=http://127.0.0.1:5000/api> .env
```

PowerShell (use exactly this; `echo` in PowerShell writes a file encoding Vite can't read):
```powershell
Set-Content -Path .env -Value "VITE_API_BASE_URL=http://127.0.0.1:5000/api" -Encoding ascii
```

### 9. Start the frontend

```bat
npm run dev
```

Open `http://localhost:5173`. Sign in as the admin, or use **Create an account** to try student or staff sign-up.

### 10. Run the tests

```bat
cd hostel-management-system\backend
pytest
```

Tests use an in-memory database and an in-memory mailbox. They never touch your data or send email.

### Running it again later

```bat
conda activate hms_env
cd /d <path>\hostel-management-system\backend
flask run
```

In a second window:

```bat
cd /d <path>\hostel-management-system\frontend
npm run dev
```

## Upgrading an existing installation

If you already run an earlier version of this project, your data and existing accounts are kept.

1. Stop both servers with Ctrl + C.
2. Replace the project's **code** with the new version. **Keep** these:
   - `backend\.env` (your secrets)
   - `backend\instance\` (your database)
   - `frontend\.env`
3. Add the new settings from `.env.example` to `backend\.env`: `FRONTEND_URL`, the account policy lines and the `MAIL_*` lines. Anything you leave out uses safe defaults.
4. Install any new packages and apply the new migration:
   ```bat
   conda activate hms_env
   cd backend
   pip install -r requirements.txt
   flask db upgrade
   ```
5. Start both servers again.

**What the migration does to existing users.** Accounts created before this version were made by an admin or the CLI, so they're trusted. The migration marks them **approved** and their email as **verified**, which means everyone can keep signing in. The migration is reversible, and a test confirms that existing users can still sign in after the upgrade.

## Email setup

The app sends four kinds of email:
- verification links
- password reset links
- staff invitations
- approval and rejection notices

### Development: the email outbox (no SMTP needed)

With `MAIL_BACKEND=file`, no real email is sent. Each email is saved as a text file in **`backend\instance\dev-outbox\`**. Open the newest file and copy the link from it into your browser.

This mode is **refused in production**. The API never returns tokens in its responses, and they're never written to the server log.

### Real email (SMTP)

Set these in `backend\.env`:

```ini
MAIL_BACKEND=smtp
MAIL_SERVER=smtp.gmail.com
MAIL_PORT=587
MAIL_USE_TLS=true
MAIL_USERNAME=your-account@gmail.com
MAIL_PASSWORD=your-app-password
MAIL_DEFAULT_SENDER=HostelHub <your-account@gmail.com>
FRONTEND_URL=http://localhost:5173
```

- **Gmail:** turn on 2-step verification, then create an **App password** and use that, not your normal password.
- **Outlook / Microsoft 365:** use `smtp.office365.com`, port 587, TLS.
- **Brevo, SendGrid, Mailgun and similar:** use the SMTP host, port, username and key they give you.

### Real email over HTTPS (Brevo API)

Some hosts, including **Render's free web services**, block outgoing SMTP ports. Use Brevo's HTTPS API instead:

```ini
MAIL_BACKEND=brevo
BREVO_API_KEY=xkeysib-...
MAIL_DEFAULT_SENDER=HostelHub <your-verified-sender@gmail.com>
```

The sender must be verified in Brevo. Delivery problems (wrong key, unverified sender) appear in the server
log as `Email delivery failed (Brevo HTTP 401: ...)`.

Emails are sent in the background, so pages respond quickly. If SMTP isn't configured or delivery fails, users still see the normal message, and the **server log** shows a clear error for the administrator (`Email delivery is not configured…` or `Email delivery failed…`).

## Accounts, sign-up and approval

```
Student:  Sign up ─► verify email ─► [office approves] ─► can sign in
                                      └─ rejected ─► sees "Registration not approved"

Staff:    Sign up with invitation ─► verify email ─────────────────► can sign in (invited role)
          Sign up without one     ─► verify email ─► admin approves and picks the role ─► can sign in
```

**Student sign-up**
- Collects: name, student ID, college email, phone, course, department, year, emergency contact, password, and acceptance of the terms.
- Duplicate emails and student IDs are rejected.
- No room is allocated and no fees are created; the hostel office does that later.

**Staff sign-up**
- Collects: name, official email, phone, employee ID, department and requested position (Staff or Warden). An invitation code is optional unless `STAFF_SIGNUP_ENABLED=false`.
- The server never trusts a role sent by the browser.
  - **With an invitation:** the invitation decides the role. The email must match the invited address, and the code works once and expires.
  - **Without an invitation:** the account gets the lowest staff role and stays **pending**. An admin chooses staff or warden when approving it.
- **Admin is never possible through sign-up.** It can only be granted later by an existing admin, from Staff accounts → Accounts → Role.

**Sign-in**
- If the password is wrong or the email is unknown, the answer is always "Invalid email or password."
- If the password is correct but access isn't allowed yet, the user is sent to a page that explains why:
  - *Verify your email* (with a resend button)
  - *Waiting for approval*
  - *Account deactivated* or *Registration not approved*
- After signing in, everyone goes to `/dashboard`, which shows the dashboard for the role the **server** returned.

**Where staff review accounts**
- **Admins** use **Staff accounts**, which has three tabs:
  - **Accounts:** change roles, deactivate, email a reset link, set a temporary password, view history.
  - **Applications:** approve with a role, or reject with a reason.
  - **Invitations:** create, list and revoke. The code is shown once.
- **Wardens and admins** use **Students**:
  - filter by approval status and email verification
  - open a pending student to approve or reject them
  - email a reset link, or view the account history.

**Password recovery**
- **Forgot password** always shows the same message, whether or not the account exists.
- A reset link is single-use, expires after 30 minutes by default, and is stored only as a hash.
- Using it signs the user out of every device.
- Changing your own password also signs out your other devices.

**Account page:** shows your profile, verification status, approval status and role. You can edit allowed fields (name and phone; for students also address and emergency contact), change your password, sign out, or sign out of all sessions.

## Roles and permissions

Every rule here is enforced **on the server**. The frontend also hides what a role can't use, but only for convenience.

| Capability | Admin | Warden | Staff | Student |
|-----------|:-----:|:------:|:-----:|:-------:|
| Sign up publicly | — | invitation or approval | invitation or approval | ✅ |
| Dashboard | staff | staff | staff, without finance | own |
| View students and rooms | ✅ | ✅ | ✅ (read-only) | — |
| Register or edit students; approve or reject registrations; deactivate; send reset link | ✅ | ✅ | — | — |
| Delete a student (no history) | ✅ | — | — | — |
| Create or edit rooms | ✅ | — | — | — |
| Allocate, transfer, check out | ✅ | ✅ | — | — |
| Fees and payments | manage | view | — | own only |
| Complaints | manage | manage | manage | file and view own |
| Publish notices | ✅ | ✅ | — | — |
| Reports, CSV exports, audit log | ✅ | — | — | — |
| Staff accounts, applications, invitations, role changes | ✅ | — | — | — |
| Edit own profile, change password, sign out everywhere | ✅ | ✅ | ✅ | ✅ |

**Safeguards**
- An admin can't deactivate or demote themselves, and the last active admin can never be deactivated or demoted.
- Deactivation, rejection, role changes and password resets end every session for that user immediately.

## API reference

All endpoints are under `/api`.
- A success response looks like `{"success": true, "data": …, "message"?: …}`.
- An error response looks like `{"success": false, "error": {"code", "message", "details"?}}`. Validation errors include `details.fields`.
- Money is an integer number of paise (fields ending in `_minor`).

**Public account endpoints**

| Method | Endpoint | Purpose |
|--------|----------|---------|
| GET | `/auth/signup-policy` | Which sign-up options are enabled |
| POST | `/auth/signup/student` | Register a student (pending, unverified) |
| POST | `/auth/signup/staff` | Register staff, with an optional `invitation_code` |
| POST | `/auth/invitations/validate` | Check an invitation code |
| POST | `/auth/verify-email` | `{token}`: confirm an email address |
| POST | `/auth/resend-verification` | `{email}`: same response whether or not the account exists |
| POST | `/auth/forgot-password` | `{email}`: same response whether or not the account exists |
| POST | `/auth/reset-password` | `{token, password, confirm_password}` |
| POST | `/auth/login` | Sign in. Error codes: `invalid_credentials`, `email_unverified`, `account_pending`, `account_disabled`, `account_rejected`, `too_many_attempts` |

**Signed-in user**

| Method | Endpoint | Purpose |
|--------|----------|---------|
| GET / PATCH | `/auth/me` | Read or update your own allowed profile fields |
| POST | `/auth/change-password` | `{current_password, new_password, confirm_password}`. Returns a new token. |
| POST | `/auth/logout` | Sign out this session |
| POST | `/auth/logout-all` | Sign out every session |

**Admin: staff accounts**

| Method | Endpoint | Purpose |
|--------|----------|---------|
| GET / POST | `/auth/staff` | List (filters: `role`, `status`, `approval`, `search`) or create directly |
| GET / PATCH | `/auth/staff/<id>` | View, or update name, phone, `is_active` or `role` |
| POST | `/auth/staff/<id>/approve` | `{role: staff\|warden}` |
| POST | `/auth/staff/<id>/reject` | `{reason}` |
| POST | `/auth/staff/<id>/send-password-reset` | Email the user a reset link |
| POST | `/auth/staff/<id>/reset-password` | Set a temporary password |
| GET | `/auth/staff/<id>/history` | Account audit trail |
| GET / POST | `/auth/invitations` | List or create an invitation (the code is returned once) |
| POST | `/auth/invitations/<id>/revoke` | Revoke an invitation |

**Students:** `GET/POST /students` (filters include `approval` and `verified`) · `GET /students/departments` · `GET /students/me` · `GET/PATCH/DELETE /students/<id>` · `PATCH /students/<id>/status` · `POST /students/<id>/approve` · `POST /students/<id>/reject` · `POST /students/<id>/send-password-reset` · `POST /students/<id>/reset-password` · `GET /students/<id>/history`

**Other modules:**
- Rooms: `/rooms`
- Allocations: `/allocations` (with `/transfer` and `/checkout`)

## Database design

There are fourteen tables, all managed by Alembic migrations. Anything that can be derived is computed when queried, not stored.

| Model | Key points |
|-------|-----------|
| **User** | Login identity for every role. Holds `email_verified_at`, `approval_status` (pending, approved or rejected), the approval note, and who reviewed the account and when. `created_via` records how it was made (cli, admin, staff, signup, invitation or legacy). `token_version` lets old tokens be revoked. Emails are unique and lowercase. |
| **StudentProfile / StaffProfile** | Role-specific details. Student ID and employee ID are unique. A staff profile records the *requested* role, which can only be staff or warden. |
| **AccountToken** | Email-verification and password-reset tokens. Only the **SHA-256 hash** is stored. Each has an expiry and `used_at`, so it works once. Issuing a new token cancels older unused ones. |
| **StaffInvitation** | Hashed, single-use and tied to one email. A database rule limits its role to staff or warden, and it can be revoked. |
| **Room / RoomAllocation** | Occupancy is counted from active allocations. A student can have only one active allocation, and the history is never deleted. |
| **FeeRecord / Payment** | Fee status and amount paid are computed. Payments are only ever reversed, never deleted. |
| **Complaint / ComplaintComment, Notice, AuditLog, RevokedToken** | As described in the sections above. |

## Security

**Passwords and tokens**
- Passwords are hashed with scrypt and must meet a strength policy, checked on both client and server. They are never logged or emailed.
- Verification, reset and invitation tokens come from a secure random generator, are stored only as hashes, expire, and work once. They never appear in API responses or server logs.

**Preventing account discovery**
- Login, forgot-password and resend-verification don't reveal whether an email is registered.
- The response time is the same either way: emails are sent in the background, and an unknown email still goes through a dummy password check.

**Rate limits**
- Failed logins: 5 per 15 minutes for each email from each address.
- Forgot-password and resend-verification: 3 per 15 minutes per email, and 20 per hour per address.
- Sign-ups: 10 per hour per address.
- Guesses at tokens or invitation codes: 30 per 15 minutes per address.

**Access control**
- Roles come only from the server.
- Every request re-checks that the account is active, approved and verified. This happens even if no token was explicitly revoked, and a test covers it.
- Sessions are revoked on logout, logout-all, password change or reset, deactivation, rejection and role change.

**Also in place**
- Every endpoint except the public ones requires a valid token. A test checks all of them.
- Secrets come only from environment variables. CORS allows only the listed origins.
- Account lifecycle events are recorded in the audit log, never with passwords or tokens.
- CSV exports are protected against spreadsheet formula injection.
- Only the email address is remembered on the login page, never a password or token. The session token is kept in `sessionStorage`, so it belongs to one tab.

## Known limitations

- **Real email needs SMTP or Brevo settings.** Until you add them, use the development outbox.
- **Free hosting:** the Render API sleeps after 15 idle minutes, and the first request then takes about a minute. Brevo's free plan sends up to 300 emails a day.
- **Rate limits are kept in memory in one server process.** `render.yaml` therefore runs one Gunicorn worker (with 4 threads). If you run several processes, use a shared store such as Redis.
- **Students can't change their own email address.** Changing it would need re-verification; staff can change it from the student's record.
- **No online payment gateway.** Payments are recorded by staff and labelled that way.
- **No frontend unit tests.** The frontend was checked with the production build and manual browser testing.

## Troubleshooting

| Problem | Fix |
|---------|-----|
| No email arrives in development | That's expected with `MAIL_BACKEND=file`. Open the newest file in `backend\instance\dev-outbox\`. |
| No email with SMTP | Check the server log for `Email delivery…` errors. For Gmail, use an App password. Check `MAIL_DEFAULT_SENDER`. |
| A link in an email opens the wrong address | Set `FRONTEND_URL` to your frontend's address, then restart the backend. |
| "Cannot reach the server" | Make sure `flask run` is running and `VITE_API_BASE_URL` matches its port. Restart `npm run dev` after changing `.env`. |
| CORS error in the browser console | Add the frontend's exact origin, such as `http://localhost:5173`, to `CORS_ORIGINS`. |
| Sign-in says "verify your email" | Open the verification link, or use "Send a new verification link" on that page. |
| Sign-in says "waiting for approval" | A warden or admin must approve the account under Students, or an admin under Staff accounts → Applications. |
| `no such column: users.approval_status` | Run `flask db upgrade` in `backend\`. |
| Port 5000 or 5173 already in use | Another copy is running. Stop it, or use `flask run --port 5001` or `npm run dev -- --port 5174`. If you change ports, also update `VITE_API_BASE_URL`, `CORS_ORIGINS` and `FRONTEND_URL`. |
| `RuntimeError: MAIL_BACKEND='file' is not allowed in production` | Production needs real email settings (`smtp` or `brevo`). |
| Render: `Production configuration is incomplete` | The log lists each missing setting. Add it under the API service's **Environment**. |
| Render: site loads but says "Cannot reach the server" | `VITE_API_BASE_URL` on the static site is wrong. Fix it, then **Clear build cache & deploy** the static site. |
| Render: CORS error in the browser console | `FRONTEND_URL` on the API must exactly match the frontend address (https, no trailing slash). |
| Render: first sign-in is very slow or times out | The free API was asleep. Wait a minute and try again. |
| Render: no emails arrive | Check Spam. Then check the API **Logs** for `Email delivery failed (Brevo HTTP ...)`: usually a wrong key or an unverified sender. |
